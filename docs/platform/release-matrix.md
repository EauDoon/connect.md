# Release matrix

Apply this matrix to each feature manifest. Mark every axis `applicable`, `not applicable` with a reason, or `unverified`; do not treat an unverified axis as a pass. The stages and claim rules are defined in the [feature lifecycle](feature-lifecycle.md).

| Coverage axis | Evidence expected before a releasable claim |
| --- | --- |
| Authority | server-side actor, scope, consent, ownership, audit, and denial paths |
| Data | schema, classification, minimization, migration, and durable-state handling |
| API | authorization, validation, idempotency/conditional behavior where applicable, errors, and OpenAPI |
| UI | explicit state, human controls, accessibility baseline, and no unsupported affordance |
| Search | public projection rules, private-data exclusion, indexing/removal behavior |
| Protocols | capabilities, MCP/A2A/discovery, and HTTP semantics agree with actual authority |
| Export | subject scope, third-party exclusion, artifact security, and evidence where applicable |
| Conceal | immediate visibility and credential-denial behavior where applicable |
| Erase | live-data disposition, holds, provider/backups, and terminal-state evidence where applicable |
| Retention | purpose, owner, duration, holds, expiry, and minimum retained data |
| Workers | idempotency, retry/dead-letter behavior, privilege, observability, and recovery |
| Ops | configuration, migration/rollback compatibility, health, logs, backup, and runbook evidence |
| Tests | relevant unit, integration, negative, contract, and deployment checks with recorded results |
| Exclusions | unavailable paths are denied and omitted from UI, search, protocols, and public claims |

Truthful claims must name the narrowest evidence-backed stage. In particular, a design contract is not implementation, an integrated implementation is not deployment verification, and a lifecycle workflow is not an export, concealment, erasure, or retention completion claim without the required recorded evidence.
